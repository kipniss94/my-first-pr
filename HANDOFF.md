## 3. Детали `.SLDPRT` — как устроено и что проверено

Порядок в `apps/api/src/processing/processors/cad-proprietary.ts`:
1. **Готовая сетка SolidWorks** (`Contents/DisplayLists`, `sldprt/display-list.ts`)
   — если она не устарела: когда число её граней не равно числу граней тела
   показанной конфигурации (`Config-<текущий swID>-Partition`), а тело
   триангулируется точно (ни одной приближённой грани), рисуется тело
   (`solidInstead`, `meta.staleDisplayMesh`). Так сетка «от прежнего состояния»
   (винт M3×5, нарисованный размером 17×24 мм; плита до последнего выреза)
   больше не показывается. Проверено: габариты сборок с такими деталями
   сошлись с записанными SolidWorks; где тело даёт приближённые грани
   (электродвигатель ЭД1К1: 126 граней против 396), остаётся сетка — она верна.
   В `C:\User\3D\SW` правило срабатывает на 82 деталях, в `Исходно` — на 241
   из 2686, исключений нет, самая долгая — 10 с.
2. Если её нет — **точная геометрия Parasolid, триангулированная у нас**
   (`sldprt/xt-reader.ts` + `sldprt/brep-mesh.ts`).
3. Если в файле ни одного тела — «пустая деталь» (`meta.emptyModel`).

**Цвета** (`display-list.ts`: `readColours`, `visualStatesColour`): сетка
отображения — архив MFC, цвета в нём — объекты `moVisualProperties_c`
(внутри: имя материала CString, байт 0–3, RGB 0, затем 1.0f). Один стоит
перед каждым телом — цвет тела. Запись грани кончается указателем на свой
цвет, по одному на «состояние отображения»: новые файлы —
`01 00 00 00 FF FF FF FF` + указатель (за 26 байт до тега следующей грани),
старые — `02 00 00 00`, затем (1, указатель), (2, указатель). Указатель:
0 — цвет тела; `класс|0x8000` — новый объект; иначе номер ранее
прочитанного объекта (MFC нумерует классы и объекты по порядку; счёт от
класса грани — его номер в теге перед второй гранью). Детали из B-rep берут
цвет детали (или общий цвет тел) из `ThirdPtyStore/VisualStates`. Яркий
цвет у «серого» металла (нержавеющий болт с чистым красным) — заглушка,
не используется. В браузер цвета идут как `faceColors` рядом с
`faceRanges` (у STEP тоже) и рисуются цветами вершин. Проверка — по
превью, которое SolidWorks кладёт в файл (`PreviewPNG`): 1427 из 1458.

Контейнеры: современный ZIP без сигнатур (`container.ts`, имена записей — UTF-8
с перестановкой полубайтов) и старый OLE (`cfb.ts`; `documentEntries()` в
`sldprt/assembly.ts` отдаёт записи любого из двух). Сжатые записи —
GUID `231dd571…` + блоки `[u32 размер][u32 сжатый][zlib]` подряд, блоков может
быть несколько (раньше читался только первый → модели > 1 МБ обрезались).

**Parasolid XT (бинарный), выведено по файлам пользователя:**
- `"PS" <int n><заголовок> <int n><ключ схемы> <short число типов> <int user fields=0>`,
  затем узлы: `<short тип>` [при первом появлении типа: `0xff` = как в базовой
  схеме, иначе `<byte число полей>` + правки `C`/`D`/`I`/`A` до `Z`; для
  совсем нового типа — имя, описание, поля, байт-флаг] [`<int длина>` для
  типов с переменным хвостом] `<индекс>` поля. Конец — узел типа 1.
- Указатель/индекс: short, хранится на 1 больше (1 = нет); > 32767 — два
  short: `(второй << 15) | (первый & 0x7fff)`. Числа big-endian.
- В описании поля число элементов: 1 = скаляр, 2 = переменный хвост, n+1 = массив из n.
- Базовые раскладки (схема 13006) — таблица `BASE_SCHEMA` в `xt-reader.ts`,
  проверена на всех 1392 потоках корпуса (partition, ghost, LocalBodies).
- Топология: `FIN.vertex` — вершина в **конце** полуребра; направление ребра =
  направление кривой × `sense` кривой; наружная нормаль = нормаль поверхности
  × `sense` поверхности × `sense` грани; грань слева от своих контуров.
- `TRIMMED_CURVE` идёт от `parm_1` к `parm_2` (бывает по убыванию).
- `INTERSECTION`: CHART — лишь опорные точки (иногда 3 на всю кривую); точки
  между ними досчитываются проекцией на обе поверхности (`onBoth`).
- `SPUN_SURF`: рабочий участок профиля `start_param…end_param`, `start`/`end` — полюса на оси.

**Триангуляция B-rep** (`brep-mesh.ts`): каждое ребро дискретизируется один
раз (сетка без щелей), контуры переводятся в (u,v) поверхности с развёрткой
периода; полосы режутся швом «вершина к вершине», шапки замыкаются через
полюс; earcut + флипы Делоне + дробление по отклонению от поверхности.
Поверхности: плоскость, цилиндр, конус, сфера, тор, NURBS, выдавливание,
вращение, offset. Грань, которую не удалось разложить, рисуется плоско (или
пропускается, если её контур наматывается на ось несколько раз — резьба).

  1 пустая «Деталь8»). `Исходно`: все детали в 3D (≈2440 по сетке SolidWorks,

## 4. Сборки `.SLDASM`

**Сохранённая графика деталей** (`sldprt/stored-graphics.ts`): сборка
(165 из 711 в `Исходно`) хранит сетки своих деталей в
`FaceTessellations/000-000-NNN` — те же треугольники, что в файле детали, в
координатах детали (проверено побайтно по габариту). `FaceTessellations/
Directory`: записи «путь экземпляра (`имя-N@родитель/…`) → 8 байт геометрии
(+8 своих у повторных) → поток и номер блока (или пусто и −1: сетка у
первой записи с той же геометрией)». Блок: номер, 8 байт геометрии, число
граней, затем грани как в DisplayLists; заголовок блока стоит прямо перед
id первой грани. Пути сравниваются без регистра и пробелов (в дереве
«R=1197-1», в каталоге «R=1197 -1»). Сервер пишет `stored.nmg.json` (одна
сетка на деталь) и `placement.stored`; `placeModels` ставит её, пока файл
детали не добавлен. Покрытие: 27 595 из 39 411 вхождений; габарит
совпал с записанным в 73 из 89 сборок (в остальных записанный больше —
вероятно, скрытые компоненты/эскизы, не разбиралось). Самая большая сборка
(АШТ, 110 МБ, 10 670 вхождений, 4,6 млн треугольников) — 2,3 с.

- Дерево — `swXmlContents/COMPINSTANCETREE` (XML; в старых файлах `…__ZLB`,
  та же обёртка кодека). `swFile` — файлы, `swModel` — файл+конфигурация,
  `swReference` — экземпляры с `swTransform` (16 чисел: строки = образы осей
  X, Y, Z, затем сдвиг в метрах = порядок `Matrix4.fromArray` three.js).
  Положение детали = произведение матриц по пути. Верхнее дерево содержит
  всю иерархию — файлы подсборок не нужны. Разбор — `sldprt/assembly.ts`.
- Виртуальные компоненты: `VirtualComp/<имя до ^>` внутри документа
  родителя, вложенно. Их геометрия строится сразу и «запекается» в NMG сборки.
- Собственная `DisplayLists` сборки — кэш тел в их собственных координатах,
  **не** сборка: не рисовать как модель.
- API (`processAssembly` в `cad-proprietary.ts`) отдаёт `native.json` с
  `placements` (деталь, конфигурация, путь, матрица в мм) и `geometry3d`;
  список нужных файлов — уникальные внешние детали.
- Веб: `placeModels` (`lib/cad/loaders.ts`) ставит копии деталей по матрицам
  (общая геометрия, свой материал), дерево по путям экземпляров;
  `NativeCadViewer` — перетаскивание папки / кнопка выбора папки, отправляются
  только нужные файлы; исправлено: готовые компоненты после перезагрузки и
  потеря результатов при массовой загрузке (`lib/assembly.ts`).
- Проверено: BT100.00.00.000 (503 экземпляра, 75 файлов) — все 344 экземпляра
  с найденными файлами на местах, совпадает с превью; PB-600 (все 22 детали
  виртуальные) открывается без файлов.

**Конфигурации.** Сборка передаёт с каждым компонентом список конфигураций,
в которых его использует (`meta.componentConfigurations` → `AssemblyComponent.configurations`
→ `JobInput.configurations` → `options.configurations`). Процессор детали
читает её `swConfiguration` (`swName` → `swID`) и для каждой нужной, кроме
показанной, строит сетку из `Config-<swID>-Partition` в `config-<swID>.nmg.json`
(`configurationMeshes` в `cad-proprietary.ts`). `meta.configurations` —
{имя: url | null (= основная)}, `meta.unavailableConfigurations` — чего в
файле нет. Веб грузит их отдельно (`RenderableComponent.configurations`), а
`placeModels` берёт модель по паре (деталь, конфигурация), иначе основную.

**Открытие многих файлов** — `apps/web/src/lib/open.ts` (`openFiles`):
сборки загружаются первыми и дожидаются результата; подсборка, которую
перечисляет (`meta.referencedFiles`) другая открытая сборка и которая не в её
`unexpandedAssemblies`, сворачивается в неё (вкладка закрывается, если в
броске больше одного файла); детали уходят `uploadComponent` в каждую
открытую сборку, где они `missing`/`failed`; остальное открывается вкладками.
Сводка (`useOpenReport`, баннер в `ViewerTabs.tsx`) публикуется сразу после
разбора, до загрузок. Вкладки — `useSessions()` в `lib/session.ts`; при
переключении `refreshSession` перечитывает задачу, а `useAssembly` вливает
серверное состояние компонентов в своё. Загрузки идут по 2 одновременно.
Бросок на окно просмотрщика — `useViewerDrop` (пропускает бросок, уже
принятый панелью компонентов: `defaultPrevented`).

**Панель компонентов** (`NativeCadViewer.tsx`): у недостающих — «Locate…»
(имя в буфер + диалог выбора файла; выбранный файл переименовывается в имя
компонента), «Search» (`search-ms:` — поиск Проводника по имени, папка
меняется и хранится в localStorage), «Copy name»; «×N» — число вхождений;
«N of M occurrences placed».

**Лимиты запросов.** Клиент (`fetchApi`, загрузки в `api.ts`) при 429 ждёт
окно из заголовков `RateLimit`/`Retry-After` и повторяет; опрос реже, когда
документов/компонентов в обработке много. Локальный лаунчер ставит
`RATE_LIMIT_UPLOADS=5000`, `RATE_LIMIT_API=20000`.

**Пути файлов.** Дерево сборки хранит, где SolidWorks держал каждый файл
(`swFile swPath`): `meta.originalPath` (сама сборка), `meta.referencedPaths`,
`AssemblyComponent.originalPath`. `packages/shared/src/paths.ts` сравнивает их с
путями внутри брошенной папки (`pathOf` в `lib/open.ts`, `Session.sourcePath`):
из одноимённых копий (Boolbotron в1/в2, библиотечные копии) берётся та, что
лежит там, где её записала сборка. Панель показывает, где лежала каждая
недостающая деталь, и общую папку («storage-1», на 3 уровня выше сборки),
которую достаточно выбрать. Locate… с файлом другого имени — только после
подтверждения, и строка помечается «Shown from …». `verify-models` сначала
ищет деталь по записанному пути относительно нынешнего места сборки.
Вкладки хранятся в `sessionStorage` (`docuview.tabs`) и возвращаются после
перезагрузки; просроченные задачи тихо закрываются.

**Проверка расстановки** — `verify-models --assemblies` отправляет детали
компонентами сборки (путь просмотрщика, с конфигурациями) и сравнивает
габарит расставленной сборки с `swBoundingBox` из её XML. Этот габарит —
сохранённое SolidWorks значение: в BT100.00.00.000 он совпадает по max X/Z,
min X совпадает, если учесть 26 скрытых компонентов, а min Y (−141 мм) не даёт
ни одно вхождение. Поэтому расхождение — повод посмотреть, а не ошибка.
Итог на `C:\User\3D\SW` (95 собранных сборок): во всех «на местах N из N
вхождений»; габарит совпал у 83. Остальные 12: конфигурации, чьих тел нет в
файле детали (Амортизатор, Крепление слота, выключатель, сборка электроники —
у последних двух проверка подставляет одноимённый toolbox-файл из другого
проекта), и волноводы ГРПЗ / BT100.01.01.200/300 на 2,7–6%, где детали точные
(сетка = тело), а габарит SolidWorks на 2–3 мм «уже» их положения по его же
матрицам — вероятно, габарит не пересчитан после правки сборки.

## 4a. Чертежи `.SLDDRW`

`sldprt/drawing.ts` + просмотрщик `cad-drawing` (`DrawingViewer.tsx`): лист —
SVG в мм (вектор, масштаб колесом по viewBox). Формат (описан в шапке модуля):
`Contents/DisplayLists` — записи `[u32 size][u32 kind]` (перо 0x0c, отрезок 4,
ломаная 6, дуга 2, шрифт 0x0a, текст 0x12 с ширинами символов, лист 0x1e);
содержимое листа идёт ДО его записи, после последней — виды. Запись вида
якорится на масштабе s: начало +10, рамки +47/+79, смещение −24, поворот −96
(нет, если единичный); лист = O + T + s·(Rᵀp). `Contents/VBLists` — рёбра видов
(корзины uiViewBucket_c; точки double, в старых файлах float). Корзина→вид: по
порядку или по направлению (знак важен) + рамке ≥90%; выносные виды — геометрия
родителя, обрезанная окружностью выноса (из аннотаций) или рамкой. Скрытые виды
и неверные — по «чернилам» картинки SolidWorks (`Images/Sheet_N`, её положение
на листе измеряется: `registerPicture`); всё, что есть на картинке и не
нарисовано, закрывается её патчами (`missingRegions`), лист всегда полный.
Знаки из библиотеки SolidWorks (запись 0x13: позиция +8, угол +36, высота
+44, строки «библиотека»/«имя» с +52) — символами (`SYMBOLS`: MOD/DIAM Ø,
PM ±, DEG °, MMC Ⓜ, GGTOL/* — знаки допусков формы) в размере соседнего
текста; сварочные GWLD/* и стрелки VIEW/GOSTR не рисуются. Корзины↔виды:
сперва по порядку (пока направление и рамка сходятся, включая виды вне
листа), потом по направлению. Покрытие картинки при поиске «дыр» — 3 px
(картинка рисует тонкие виды толще и может сидеть на пиксель в стороне;
при 2 px на фланце боковой вид уходил в патч).

Рёбра в VBLists: шаг между соседними точками до 10 м (было 0,5 м — у
воздуховода 4387 мм терялись длинные прямые рёбра, и контур короба уходил в
патчи). Мусор, который раньше отсекал этот порог, — массивы тесселяции
`[12][100][2][n]`: их «2» читалось как число точек ребра; теперь позиция
сразу после `12, 100` пропускается явно.

Второй вид записи листа (1 чертёж из 6): перо 0x0c со стилем линии, сразу
за его строкой — высота, ширина (f64) и имя листа (`readSheets`).

**Виды с разрывами** (`readBreaks`, `breakLayout`, `assignBroken`): рёбра в
корзине хранятся целыми, рамка вида — уже сжатая, поэтому обычное
распределение корзин их не находит. Линии разрыва — объекты `moBreakLine_c`
в `Contents/Definition`, имя как у первого («Линия разрыва1»…); через 215
байт после имени — 4 точки (x, y, 0): концы двух линий в единицах листа от
начала вида; горизонтальные линии — разрыв по y, их длина = ширина вида.
Своя запись вида (есть не у всех): `FF FF FF FF`, зазор f64, размер зигзага;
за 12 байт до зазора — стиль линии, за 60 — несжатый габарит вида, а
заканчиваясь за 116 байт — число кусков и по (dx, dy, 0) на кусок. Правило
SolidWorks (сходится с записанными сдвигами до 1e-7): первый кусок
сдвигается на половину всего вырезанного (Σ полос − k·зазор), каждый
следующий — меньше на (полоса − зазор); вид сохраняет середину. Без записи
зазор берётся из других записей файла, иначе подбирается по рамке. Корзины —
сначала те, что точно по ширине линий разрыва, начиная с видов с
наименьшим выбором (у вида и его разрезов одно направление).

Проверка на корпусе: пройти все `.slddrw` через `readDrawing` + `sheetSvg`
(скрипт `drw-all.mts` был в scratchpad сессии), считать виды и
`sheet.patches` (прямоугольники `[x0, y0, x1, y1]` в метрах). Последний
прогон, 1019 чертежей из `Исходно`, 1513 листов: 0 падений, 13 без
DisplayLists (превью); видов 3779 — 3293 из файла, 426 по картинке, 60
скрытых; листов с патчами 502, листов полностью векторных 765. Самый долгий
файл — 12 с (шкаф АШТ, десятки листов). Дальше: штриховка выносных видов
(сейчас редкая), знаки сварки, касательные рёбра (SolidWorks их часто

## 4b. Интерфейс: тема, язык, размеры, редактирование (сделано)

- **Тема и язык** — `lib/prefs.tsx` (`useT()`: `t`, `tp` для чисел с тремя
  русскими формами, `tx` для шаблонов с React-узлами; `translate()` вне React),
  cookies `docuview-lang` / `docuview-theme` (`lib/prefs-keys.ts`) читает
  `app/layout.tsx`, поэтому сервер сразу рисует нужное. Без cookie язык — по
  Accept-Language. Словарь `lib/i18n-ru.ts`: ключ — английский текст из кода;
  сообщения сервера с числами — `RU_PATTERNS`. Проверка, что всё переведено:
  собрать все `t('…')` из `apps/web/src` и сверить со словарём (скрипт был в
  scratchpad: `keys.cjs`). Страницы сайта (about, privacy, terms, *-viewer) —
  серверные компоненты: язык из `lib/server-lang.ts`, текст — две версии в
  файле страницы или `serverT()` (`lib/i18n-server.ts`).
  Светлая тема — подмена CSS-переменных `ink`/`mist` в `globals.css`
  (`:root[data-theme='light']`); фон 3D и сетка — `PALETTES` в `scene.ts`.
- **Пустая полоса справа** была резервом под рекламу (`ViewerAdRail`), теперь
  рисуется только при `NEXT_PUBLIC_ADS_ENABLED=true`.
- **Поиск деталей сборки в папке** — `lib/folder-scan.ts` (File System Access
  API: обход только нужных имён; запасной путь — `webkitdirectory`), выбор
  версии — `VersionChooser` в `components/cad/ComponentsPanel.tsx`
  (`suggestedCopy`: по месту, записанному в сборке, иначе самый новый).
- **Размеры** — `lib/cad/measure.ts`: топология детали (сварка вершин, грани
  из `faceRanges` или наращиванием по нормалям для сеток, рёбра — швы между
  гранями, разбитые на углах и на переходах прямая/дуга), распознавание
  (плоскость/цилиндр/конус/сфера подгонкой; отрезок/окружность/дуга),
  варианты размеров `measureOptions`. Сцена (`scene.ts`, «smart measuring»):
  подсветка под курсором, выбор до двух, живой размер, Space/колесо/Shift+колесо,
  Enter/Esc. Панель над моделью — `LiveMeasurePanel.tsx`, подсказка —
  `MeasureHelp.tsx`. Выше 600 000 треугольников в детали — только точки.
- **Редактирование** — Office на сервере: `processing/ooxml-edit.ts`
  (`readEditable`/`applyEdits`, правка XML через @xmldom: меняется только
  отличающийся кусок текста внутри прогона), маршруты `GET /files/:id/editable`,
  `POST /files/:id/edited` (JSON до 16 МБ только на нём). Клиент:
  `DocEditor`, `SlidesEditor`, `TextEditor`, правка ячеек в `SheetViewer`,
  `lib/edit.ts` (`saveToDisk` — showSaveFilePicker или скачивание). PDF — в
  браузере, `lib/pdf-edit.ts` (pdf-lib + fontkit, шрифт Liberation Sans
  копируется из pdfjs-dist в `public/fonts` скриптом `copy-pdf-worker.mjs`):
  старый текст вырезается из потока страницы (`lib/pdf-erase.ts`: разбор
  потока, состояние текста, ширины глифов — из шрифта или метрик стандартных
  14 через `@pdf-lib/standard-fonts`; фрагмент — глифы подряд от его начала,
  только вперёд, в пределах его ширины; каждый заменяется сдвигом TJ той же
  ширины), новый пишется на его место; что не нашлось (XObject, шрифт без
  ширин) — закрывается белым. Страницы удаляются. Проверено на 200 PDF
  чертежей SolidWorks: 999 из 1000 фрагментов вырезаны целиком, соседний
  текст не сдвинут.
